# Phase 4: Mock L3KVG Test Harness & Operation Verification

## Objective
To ensure the correctness of the iRODS L3KVG database plugin before a full iRODS deployment, we will build a comprehensive testing harness. This harness will load the compiled plugin (`libirods_database_plugin_l3kvg.so`) and test its `DATABASE_OP_*` interfaces against a mock L3KVG ZeroMQ server. This verifies the complete pipeline: from iRODS struct translation in `db_plugin.cpp`, through `CatalogFacade`, to the final Snowflake ID and BSON payload sent over ZMQ.

## 1. Mock L3KVG ZeroMQ Server
We will construct a lightweight, embedded ZMQ server (`MockL3KVGServer`) within the test suite.
*   **Protocol:** It will bind to a local IPC or TCP socket (e.g., `tcp://127.0.0.1:5556`).
*   **Behavior:** It will listen for the ZMQ messages generated by `RemoteL3KVClient`. Instead of writing to an LSM tree, it will decode the Snowflake IDs and BSON buffers and store them in memory.
*   **Verification:** Tests will query the `MockL3KVGServer` to assert that the correct nodes, attributes (compact short-keys), and edges were created with the expected deterministic Snowflake IDs.

## 2. Plugin Loading & Setup
The test harness will instantiate the plugin exactly as the iRODS agent would.
*   **Instantiation:** Use `dlopen` or directly link the test binary to `plugin_factory()` to get an instance of the `l3kvg_database_plugin` class.
*   **Configuration:** Provide a mocked `irods::plugin_context` and a mocked `server_config.json` that points the plugin to the `MockL3KVGServer`'s ZMQ endpoint.
*   **Initialization:** Invoke `DATABASE_OP_START` to verify that the Smart Client connects to the mock server and successfully bootstraps the local zone and admin user.

## 3. Operation Test Suites
We will implement GTest suites targeting specific operational categories. Each test will construct the necessary legacy iRODS structs (e.g., `dataObjInfo_t`), invoke the plugin operation, and then assert the mock server's state.

### Suite 1: Identity & Authentication (`test_plugin_identity.cpp`)
*   **Operations:** `REG_USER`, `CHECK_AUTH`, `MOD_USER`.
*   **Verification:** Ensure Snowflake IDs are correctly prefixed with the Zone Hash. Verify BSON uses `n` for name, `p` for privilege level.

### Suite 2: Data & Metadata Management (`test_plugin_data.cpp`)
*   **Operations:** `REG_DATA_OBJ`, `REG_REPLICA`, `REG_COLL`, `ADD_AVU_METADATA`.
*   **Verification:** 
    *   Ensure the logical `dataId` and physical `replNum` generate distinct but related nodes.
    *   Verify structural edges (e.g., `CONTAINS`, `HAS_REPLICA`, `STAYING_AT`, `ANNOTATED_WITH`) are correctly requested via ZMQ.

### Suite 3: Cross-Zone Federation (`test_plugin_federation.cpp`)
*   **Operations:** `START` (with a multi-zone config), `REG_DATA_OBJ` (with a foreign zone).
*   **Verification:** Ensure the plugin routes requests for a foreign zone (e.g., creating a remote ACL) to the appropriate mock ZMQ endpoint based on the 16-bit cluster ID prefix.

## 4. Execution Plan
1.  Implement `MockL3KVGServer` in a new `tests/mock_l3kvg.hpp`.
2.  Create the `PluginTestFixture` base class to handle plugin initialization and mock server lifecycle.
3.  Implement the test suites one by one, filling in the missing Smart Client translation logic in `CatalogFacade.cpp` and `db_plugin.cpp` as tests dictate.
